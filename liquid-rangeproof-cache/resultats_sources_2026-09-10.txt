Source-checking notes, Liquid Network range-proof cache exploit
=================================================================
Run 2026-09-10, alongside reconstruct_exploit.py.

1) DefiLlama hacks feed (primary tracker consulted first, api.llama.fi/hacks,
   fetched live 2026-09-10 and re-sorted by date):

   2026-09-06 | Liquid Network | 320000000 | ['Liquid'] | Bridge & Cross-Chain
   | Unbacked Cross-Chain Mint

   This is the only DefiLlama row for this incident: one row, $320,000,000,
   dated 2026-09-06. Not yet present in this repo's index.

2) Root cause, primary source: ElementsProject/elements is the Liquid
   sidechain's own official open-source implementation (the "Elements"
   project, github.com/ElementsProject/elements). Its own GitHub REST API
   was queried directly (api.github.com/repos/ElementsProject/elements),
   not a mirror, not a press paraphrase:
     - GET /releases/tags/elements-23.3.4 -> published_at 2026-09-09T03:14:44Z,
       body lists PR #1600 as the fix.
     - GET /pulls/1600 -> merged_at 2026-09-08T19:06:54Z, title "sigcache:
       harden range proof cache keys and add -norangeproofcache option",
       body explicitly describes the bug: the range-proof/surjection-proof
       cache hashed its arguments via raw CSHA256 concatenation instead of a
       length-prefixed CHashWriter, so "distinct argument tuples with
       byte-identical raw concatenations no longer collide to the same cache
       key" after the fix (implying they did collide before it).
     - GET /security-advisories -> empty list, i.e. no formal GHSA has been
       published on this repo for the incident as of this run (4 days after
       the exploit). Noted, not treated as an absence of a primary source:
       the merged PR and tagged release are themselves primary, official
       repo content.

3) Liquid Network's own incident report: posted on X by the project's own
   account, @Liquid_BTC ("Liquid Network"), thread titled "LIQUID NETWORK
   UPDATE: INCIDENT REPORT," status as of September 8, 2026, 19:10 UTC.
   Direct fetch of https://x.com/Liquid_BTC/status/2097404704028545175
   returned HTTP 402 (Payment Required) to an automated request. Retried
   once via a different method: (a) Twitter's public syndication endpoint
   (cdn.syndication.twimg.com/tweet-result?id=...) returned an empty object,
   (b) a Nitter mirror (nitter.net) is offline. Neither alternate fetch
   route worked. What is used instead: two independent web search queries,
   worded differently ('"15:53:10 UTC" Liquid block 4,050,336 incident
   report' and '"4,050,336" Liquid Network incident report what happened'),
   both returned the identical exact string as the indexed page title of
   that X status URL: 'LIQUID NETWORK UPDATE: INCIDENT REPORT Status as of
   September 8, 2026, 19:10 UTC What Happened? On September 6, 2026 at
   15:53:10 UTC (Liquid block 4,050,336), a vulnerability in the open-source
   Elements software related to how Liquid nodes cache range proof
   verifications...'. Getting the identical verbatim string back from two
   differently-worded queries is what this entry relies on as the actual
   tweet text, not a single paraphrase. This is the same kind of access
   limitation already logged in this repo's Allbridge entry (H2: SlowMist's
   article fetched via a mirror after a direct 403), documented here rather
   than silently worked around.

   One of the search results surfacing this quote was a GitHub gist
   ("kimi_report_liquid_hack.md" by a personal account) containing a
   specific txid and a "clock skew" theory to explain away the 2-hour gap
   this entry independently found between that quote and the Liquid block's
   own chain timestamp. That gist is NOT a primary source (not the
   project's own repo, not a named security team) and its own numbers do
   not even reconcile (it claims ~73 minutes of skew against a gap this
   script measures as exactly 2 hours/120 minutes from chain data alone).
   It is excluded from this entry's evidence entirely; the one specific
   txid it names (f24a4b17...e183f) does independently check out as real
   when queried directly (it is genuinely in block 4,050,336), which is
   coincidental corroboration of that one fact, not a reason to trust the
   gist's interpretive claims.

4) Federation multisig structure, primary source: Blockstream's own Help
   Center article "How does the Liquid Federation's multisig work?"
   (help.blockstream.com) describes an 11-of-15 multisig for regular
   peg operations plus a timelocked emergency-backup path. This matches,
   witness-script-op-code-for-op-code, what reconstruct_exploit.py decodes
   live from the federation address's own transaction inputs (Step 3): an
   11-of-15 OP_CHECKMULTISIG branch, an OP_IFDUP/OP_NOTIF/OP_CSV/OP_VERIFY
   timelock gate, and a 2-of-3 OP_CHECKMULTISIG emergency branch.

5) BTC/USD conversion: CoinGecko's public API (api.coingecko.com), live
   price at script-run time and the historical daily snapshot for
   2026-09-06, both fetched directly by the script, not copied from a press
   figure. The live price ($77,809-77,821 across separate fetches on
   2026-09-10) and the 2026-09-06 historical snapshot ($79,821.70)
   are both within the range press coverage cites ($78,000-79,930), an
   independent cross-check rather than a re-statement of it.

6) What was NOT independently confirmed: the exact Liquid-sidechain
   transaction that minted the unbacked L-BTC, and its blinded amount.
   Block 4,050,336 contains 7 transactions, all using Confidential
   Transactions; public Esplora access alone does not expose blinded
   amounts, and no primary source found here names a specific txid as "the"
   fraudulent mint. This entry does not claim to have identified it.
   Likewise, press attribution of the peg-out authorization key used to
   SideSwap specifically is not re-derived here; it rests on press and
   named-security-team coverage (Halborn, CertiK) not independently
   traced on-chain in this entry, and is flagged as such in the README's
   Caveats section.
